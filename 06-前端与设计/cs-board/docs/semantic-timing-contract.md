# 旁白驱动动态 PPT 契约

版本：2.0<br>
适用范围：网页工作台“动态信息图”模式<br>
真实时间基准：最终用于成片的 `voice.wav`

## 1. 固定生产顺序

以下四步不得颠倒或合并：

1. **短语时间表**：旁白生成完成后，先将全文拆成短语，并为每条短语生成真实音频起止时间。
2. **内容结构**：模型基于已经编号的短语，梳理章节、浓缩每页中心句、列出关键词，并只引用短语编号作为触发时间。
3. **Remotion PPT**：程序先确定每页文字、布局、插图槽位、元素入场顺序和逐帧时间，生成可独立审查的 PPT 规格。
4. **PPT 插图**：图片模型最后按已经确定的插图槽位生成纯插画，不能反过来决定页面结构。

动态信息图因此被定义为“带真实旁白时间的动态 PPT”，而不是一张由图片模型自由发挥的关系图。

## 2. 第一步：完整短语时间 JSON

1. 系统必须先生成完整旁白，再分析时间。
2. 旁白经过 16kHz、单声道 PCM 转换，由本地 Whisper.cpp `medium` 模型以 DTW token 时间为基础输出有效 UTF-8 的词组边界时间。中文不能直接按单 token 文本切分，否则多字节字符可能损坏。
3. 系统将原文切成较短语义短语，为每条短语输出：`id`、`text`、真实起止毫秒、真实起止帧、字符匹配覆盖率与识别置信度。
4. 数字与其中文读法视为同一内容，例如 `5` 与“五”；繁体与简体也统一后再匹配。
5. 单个短语若被识别成近音词，只有在前后短语均高置信对齐、且中间存在唯一连续语音边界时，才允许采用该真实边界；结果必须标记 `boundary_source: neighboring-word-boundary`，不能插值估算。
6. 该步骤完全独立于页面规划。没有 `phrase-timeline.json`，不得调用内容结构模型。

## 3. 第二步：内容结构与关键词时间

每页遵循四个内容动作：

1. 提炼一个核心观点 `core_idea`；
2. 将它写成一句清晰的屏幕中心句 `page_title`；
3. 决定 PPT 的视觉呈现 `visual_strategy`；
4. 说明它如何承接上下页 `narrative_link`。

一般以本页第一条短语作为中心句依据。每个关键词包含 `label` 和 `trigger_phrase_id`；模型只能选择第一步已经存在的短语编号，不得输出或估算毫秒、秒数和帧号。

当开头明确承诺“以下 N 项”，且后文存在连续的“1、2、3……”章节时，总览页关键词由程序直接提取这些章节名称。模型不得将“舒尔特方格训练”等章节名改写成“视觉搜索”等能力或效果词。

## 4. 关系与箭头

`relationship_type` 默认必须为 `none`。

- 普通并列清单、训练名称、特征、效果解释：`none`，禁止箭头；
- 原文明说“首先、然后、最后”或“第一步、第二步”：可以使用 `sequence`；
- 原文明说“因为、所以、导致、因此”：可以使用 `cause`；
- 对比和层级可使用分栏或空间层次，但不自动添加方向箭头。

即使模型错误选择 `sequence` 或 `cause`，程序也必须检查本页原文是否存在对应关系词；没有证据就强制改回 `none`。

插图提示词始终禁止箭头、连接线、流程线、文字、项目符号和 UI。任何确实需要的结构关系都由 Remotion 绘制。

## 5. 第三步：Remotion PPT

每个页面必须先形成 `deck-spec.json`，其中包括总标题、章节标题、中心句、关键词、页面布局、关系类型、插图槽位、页面起止帧，以及每个元素对应的真实旁白 Cue。

总览页采用左侧纵向清单、右侧主题插图。它不是自动关系图，因此清单与插图之间不画箭头。

### 5.1 通用版式语法

页面不能全部退化为“左文字＋右插图”。内容模型按语义从以下版式选择，Remotion 必须分别实现不同空间结构：

- `question`：问题、悬念、反问和章节开场；
- `focus` / `principle`：单一强观点、定义、原则与中心法则；
- `comparison`：双方、正反、前后或方案对照；
- `evidence` / `case`：论点与证据、案例、数据或评价；
- `layers`：层级、深浅、逐层递进；
- `path` / `flow` / `timeline`：原文明示的步骤、阶段或时间过程；
- `cause` / `cycle`：明确因果或循环；
- `overview` / `summary`：全文架构和结尾收束。

`composition` 再决定插图与文字的空间关系：`split-right`、`split-left`、`center-stage`、`top-bottom`、`full-width`。相邻页尽量改变空间组织，但语义适配优先于形式变化。

分栏布局的文字列必须按最长可见词条计算实际宽度。短标签和证据条使用内容宽度，禁止为了填满网格而横向拉伸；释放出的空间优先扩大插图。只有长句、对照表或多列数据才允许占用宽文字列。

同一页内的 Cue 采用“累积式动态 PPT”：已有元素保留，旁白讲到新的关键词、证据、风险标签或结论时再增加一层。不同版式使用不同入场方向与强调动作。

## 6. 声音到帧

正式成片固定为 30fps。元素入场帧定义为：

`start_frame = ceil(spoken_start_ms × 30 ÷ 1000)`

使用向上取整保证元素不会早于触发短语。元素出现后停留到本页结束；后续 Cue 只改变当前强调状态。

第 2 页及以后以该页第一条短语的真实语音起点开始。两部分之间存在停顿时，上一页保持完整画面，不提前翻页。

## 7. 第四步：插图

图片模型接收已经完成的单页 PPT 内容和插图槽位要求。插图只负责提供具象视觉主体：不提炼关键词、不决定布局、不建立观点关系、不生成文字或箭头，也不得改变 PPT 结构。

## 8. 字幕与质量门槛

字幕可选。启用时直接使用 `phrase-timeline.json` 的真实起止时间，不按字数估算。

强制门槛：

- 整篇原文字符匹配覆盖率不低于 72%；
- 短语必须含有足够的真实匹配 token；近音误识别只允许使用前后强锚点夹定的真实语音边界；
- 页面必须按顺序、连续并完整覆盖全部短语；
- 每个 PPT 元素必须绑定本页短语编号；
- 后一页真实起点必须晚于前一页。

任意条件不满足时任务失败。系统不得悄悄退回按字数、页长或平均间隔估算。

## 9. 可审查产物

每个动态 PPT 任务目录保留：

- `alignment.tokens.json`：Whisper.cpp 原始 token 时间戳；
- `phrase-timeline.json`：第一步完整短语—音频时间表；
- `plan.json`：第二步内容结构及最终真实时间；
- `content-timeline.json`：每页中心句、关键词及元素 Cue；
- `deck-spec.json`：插图生成前已经确定的 Remotion PPT 规格；
- `boards.json`：第四步插图提示词；
- `remotion-props.json`：最终渲染参数；
- `subtitles.srt`：仅在用户开启字幕时生成。

所有报告中的 `estimated_fallback_used` 必须为 `false`。
