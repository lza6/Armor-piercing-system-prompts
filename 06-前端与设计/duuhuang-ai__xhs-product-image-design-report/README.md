# 小红书商品图设计决策报告（xhs-product-image-design-report）

> 一个小红书商品图分析 Skill：你给多个小红书商品链接 / 截图 / 自家商品资料，它采集公开字段与图片，逐图拆解竞品主图与详情图在解决什么购买问题，并产出一份中文 HTML **商品图设计决策报告**，告诉你自己的主图、副图、详情页长图该怎么拍、怎么排、哪些表达必须有证据。

* * *

## 核心能力

采集公开字段与图片 → 逐图拆解设计逻辑 → 给出自家商品图设计方案 → 输出独立中文 HTML 决策报告。

## 适用场景

| 场景 | 说明 |
| --- | --- |
| 竞品主图拆解 | 批量看同行主图分别在解决什么购买疑虑 |
| 详情页长图规划 | 规划自家详情页 10 屏顺序与每屏任务 |
| 拍摄清单 | 把「必须拍 / 必须确认 / 不要写」落成执行清单 |
| 证据边界管理 | 纯银、不过敏、爆款等强表达必须有证据才能写 |

## 快速安装（Codex / WorkBuddy）

把下面这段命令复制到 **Codex** 或 **WorkBuddy** 的终端执行即可（目录名即 Skill 名，必须保持中文 `小红书商品图设计决策报告`）：

```bash
git clone https://github.com/duuhuang-ai/xhs-product-image-design-report.git ~/.workbuddy/skills/小红书商品图设计决策报告
```

执行后**重载 / 重启会话**，Skill 即以「小红书商品图设计决策报告」生效。

> **Codex 用户**：把目标路径换成 Codex 的 skills 目录即可（目录名不变）。

## 依赖与准备

采集用**浏览器自动化**（非小红书官方 API），不走官方接口：

- **Node.js** + `npm` / `npx`。
- `playwright` 包或环境中已有的 Playwright CLI。
- 可访问 `xiaohongshu.com` 的网络；商品页不可公开访问时需要已登录的浏览器会话。
- 若平台风控 / 登录拦截导致采集失败，改用手动提供的截图 / 图片，并在报告中标注来源为「用户提供图片 / 截图」。

**无需 API Key**，也不读取任何平台私有数据（评论、后台指标、订单数据、隐藏字段），除非你主动提供。

## 使用方式

### 触发词

`小红书商品图设计决策报告`、`商品图设计分析`、`对比小红书竞品主图`、`帮我规划详情页长图`、`竞品详情图拆解`，或给多个小红书商品链接说「出设计决策报告」。

### 输入要求

仅接受小红书商品分析来源（**不**用于淘宝 / 天猫 / 京东 / 抖音 / 拼多多 / 亚马逊 / Shopify 等）：

- 小红书商品链接 `https://www.xiaohongshu.com/goods-detail/...`，建议 3–10 条。
- 每个商品的导出截图 / 图片（实时采集被挡时用）。
- 你自己的商品资料：名称、类目、目标人群、价格带、SKU、材质、包装、发货 / 售后规则。
- 你的证据：真实商品图、供应商规格、检测报告、材质证书、包装图、买家评价摘录、销量 / 点击 / 转化数据。

缺自家资料或证据时，继续做竞品分析，并明确标注假设与证据缺口。

## 工作流

1. **建工作文件夹**：`小红书商品分析-{YYYYMMDD-HHMMSS}/` 含 `输入资料/`（商品链接、我的产品资料、我的真实证据、竞品图片）与 `输出结果/`。
2. **采集公开字段与图片**：实时链接优先用 `scripts/collect-xhs-goods.js`，移动视口先开、等懒加载、存整页截图、抽文本 / 图片 URL / 背景图 / 渲染尺寸，图片存 `输入资料/竞品图片/商品N_短标题/`，失败记 `图片采集记录.md`。被挡则切手动截图并标注来源。
3. **归一化证据**：每个商品一条记录（链接、名称、价格、销量、店铺、SKU、主图 / 详情图路径、缺失标注），原始字段与推断结论分开。
4. **拆解图像逻辑**：主图任务（点击 / 风格 / 第一印象 / 清晰）、副图任务（佩戴 / SKU / 尺寸 / 材质 / 结构 / 包装 / 售后 / FAQ）、解决的购买疑虑（好不好看 / 能不能戴 / 怎么选 / 值不值 / 是否真实 / 收到什么）、设计套路、证据边界。核心判断是「这张图在解决什么购买问题」，不是「哪张更好看」。
5. **给设计方案**：主图 1+5 计划、详情页 10 屏顺序、执行清单、证据缺口。
6. **构建 HTML 报告**：顶部结论指标、商品级横向对比、主图 / 详情图证据墙（每商品一行、链接可见、图比三列墙更大）、维度核对、对方为什么这样设计、竞品打法地图、我的商品图怎么设计、详情页模拟布局（手机框纵向滚动 + 桌面两列网格）、执行清单。布局细节见 `references/report-structure.md`。
7. **校验**：确认 HTML 存在、商品链接都在、本地图片路径有效、必含章节齐全、缺失字段如实标注而非当作事实。

## 采集脚本用法

```bash
node scripts/collect-xhs-goods.js \
  --urls-file 输入资料/商品链接.txt \
  --out-dir 输出结果
```

- `--urls-file`：每行一个小红书商品链接，支持 `#` 注释行。
- `--out-dir`：输出目录，写入 `公开字段抽取.json` 与每张商品整页截图。
- 若在 Codex 受管运行时运行，用受管 Node 并把 `NODE_PATH` 指向其 node_modules。
- 仅采集**可见公开页**信息；不声称能拿到私有数据。

## HTML 报告必含章节

1. 报告摘要（1–2 句结论 + 商品数 / 图片样本数 / 可复用打法数 / 推荐详情屏数）
2. 商品级横向对比（每商品一张卡：图、标题、价格、销量、店铺、材质 / 规格、打法摘要、原链接）
3. 主图 / 详情图证据墙（每商品一行，8–10 图带说明，链接可见）
4. 报告维度核对（已覆盖 / 待补充）
5. 对方为什么这样设计（设计做法 / 为什么 / 解决的问题 / 我能不能学）
6. 竞品打法地图
7. 我的商品图应该怎么设计（图序 / 页面任务 / 核心文案 / 画面设计 / 需要素材证据 / 设计判断）
8. 详情页模拟布局（左手机框纵向滚动，右桌面两列网格；不用横向轮播）
9. 执行清单（必须拍 / 必须确认 / 不要写）

报告名：`输出结果/小红书商品主图详情图设计决策分析报告.html`；迭代版本加 `_v2` / `_v3` 并说明推荐版本。

## 关键执行边界（Hard Rules）

- 只用于小红书商品分析，不套其他平台。
- 采集用浏览器自动化，不声称有官方 API 或能读私有数据。
- 实时采集被挡时切手动截图，并标注「用户提供图片 / 截图」。
- 核心判断是「解决什么购买问题」，不是「哪张更好看」。
- 强表达（纯银 / 不过敏 / 爆款等）必须有证据才能写。
- 缺失 / 不确定字段如实标注，不把推断当事实。

## 故障排查

### 实时采集被拦

原因：登录 / 验证码 / 反爬，或商品页不可公开访问。

处理：用已登录浏览器会话，或改为你手动提供截图 / 图片，报告中标注来源。

### 图片下载不全

原因：懒加载未触发、CDN 限制、视口问题。

处理：脚本等待懒加载并整页截图兜底；缺失部分用你提供的截图补齐。

### 报告图片裂图

原因：本地图片路径与报告引用不一致、或相对路径错误。

处理：校验步骤会比对报告引用的本地图片路径是否真实存在；缺失则补齐后重建报告。

## 完整检查清单

- 给了 3–10 条小红书商品链接或对应截图
- 提供了自家商品资料（名称 / 类目 / 价格带 / SKU / 材质 / 包装 / 售后）
- 提供了可支撑强表达的证据（材质证书 / 检测报告 / 真实图 / 评价）
- 实时采集可用，或已切手动截图并标注来源
- 环境有 Node + playwright（用脚本时）
- 报告已含 9 个必含章节
- 缺失字段已如实标注而非当作事实
- 强表达均有证据支撑
