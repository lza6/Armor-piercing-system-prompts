# 确认是代码缺陷时怎么办

## 判定条件（满足任意一条才算）

1. **证据链完整但结论矛盾**：配置正确、依赖装好、服务在跑，同一操作仍稳定失败。
2. **内部异常**：日志里是类型错误 / 空指针 / 断言失败 / 未捕获异常
   （`app.uncaught_exception`、`app.unhandled_rejection`、`client.render_error`），
   而不是来自上游服务或用户配置的报错。
3. **可以用源码解释的错**：读实现能指出哪一行逻辑不成立（例如错误分支写反、
   异常被吞掉导致状态永远不变）。这时给出 `文件:行号`。
4. **旧版本已知修复**：`CHANGELOG.md` 里已有对应修复条目，用户版本的 `omi version` 早于它。

**反例（不要写工单）**：任何"请先配置/下载/启动"类报错、上游 4xx/5xx、网络超时、
磁盘满、用户自己的工作区/文件问题。

## 先给出临时绕行

即使用户需要升级才能根治，也要先说清**现在能怎么用**（换后端、换模型、手动装依赖、
清状态重试、暂时不用该功能）。不要只丢一句"等修复"。

## 话术模板（告知用户）

> 这个问题不是配置问题，属于程序缺陷（证据：`<日志文件:事件名>` / `<代码位置>`）。
> 需要升级程序才能解决，当前版本没有可用的绕过方法。
> 建议：`omi update` 升级到最新版 / 到 <仓库 issues 地址> 反馈（附上诊断报告）。
> 临时办法：<能绕开就写，绕不开就写"暂无可绕行方案">。

## 工单/反馈模板

```
标题：[<子系统>] <一句话现象，含报错原文>

版本：<omi version 输出> · 渠道 <dev/canary/stable> · <platform/arch>
时间：<出问题的时间点>

复现步骤：
1. ...
2. ...

期望：...
实际：...

证据（粘贴时删掉提示词、本地路径等隐私）：
- 统一日志（omi logs --level error --limit 50 -v）：
    <ts> <level> <source> <event> <message> + detail
- 诊断报告（bun run --cwd apps/studio scripts/omni-diag.ts）：
    关键几节（环境 / 相关子系统的失败记录 / 媒体服务状态）
- 数据库记录：<表>#<id> status/error 列原文
- 代码位置（如果能定位）：<file:line>

已排除：
- 配置已就绪（哪些 key 已填，密钥不贴）
- 依赖已安装（引擎/二进制版本）
- 重启应用 / 重启推理服务器后仍复现
```

> ⚠️ 提醒用户：`app.log` 与诊断报告含本地路径和提示词（密钥已自动脱敏成 `***`），
> 公开渠道反馈前先扫一眼。

## 修完之后

改代码修的路径：

1. 先写一条能稳定复现的断言（单测 / 冒烟脚本），再改；
2. 失败路径上补日志（`logEvent({level:"error", source, event, message, detail})`，
   见 `apps/studio/src/bun/app-log.ts`）——**没有日志的失败路径本身就是 bug**，
   下次同样的问题还会"查不出来"；
3. 跑 `bun run lint && bun run typecheck && bun run test`，
   涉及文档/CLI 时再跑 `bun run --cwd apps/studio test:smoke`；
4. 在 `CHANGELOG.md` 记一条（用户侧"升级后已修复"的依据）。
