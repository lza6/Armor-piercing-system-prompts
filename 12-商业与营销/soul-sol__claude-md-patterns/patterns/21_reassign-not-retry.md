# 21. Reassign, not retry
**Problem:** Orchestrators resend the same failed task to the same worker without changing any input. Repeated approval waits, tool mistakes, or blind spots consume time while producing no new evidence.
**The rule (paste into CLAUDE.md):**
```text
Track attempts by <TASK_ID>, worker identity, failure signature, changed variable, and result. Permit one retry by the same worker only after changing a decision-relevant variable, such as clarifying SCOPE, adding a missing file, correcting <VERIFY_COMMAND>, supplying the observed failure, or removing an invalid assumption. Never repeat an identical task, prompt, context set, command, and worker combination. After the same worker produces the same failure signature twice, stop assigning that task to that worker and mark it `REASSIGN_REQUIRED`. Confirm that the prior worker has exited and cannot continue writing, then assign the task to a different eligible worker with the prior attempts, verified facts, unchanged scope, and explicit acceptance criteria. Reassign immediately, without consuming a same-worker retry, when the blocker is specific to that worker’s availability, quota, authentication, unsupported tool, or permission mode and another authorized worker can execute the task. Preserve both attempt receipts, the changed variable, failure signatures, prior worker termination evidence, new worker identity, and final verification. If no eligible worker remains, stop and report the exact external blocker; do not disguise repeated retries as persistence.
```
**Why it binds:** This rule converts “try again” into a bounded state machine. A retry must buy information by changing one recorded variable, and the second matching failure forces a different executor. After the 2026-08-18 plan-and-approval stall, sending the same ambiguous request again would preserve the cause; the useful retry adds the autonomy and completion contract. A second recurrence then demonstrates a worker-specific mismatch and triggers reassignment. Confirming the old writer stopped prevents two workers from racing over the same files.
**Variations:**
- Monorepo: require reassignment into a separate worktree whenever the previous attempt left a partial diff.
- Solo: if no alternate worker exists, switch to direct local execution after the two-attempt record instead of a third prompt.
- Team: maintain a capability matrix so quota, tool, or permission failures route directly to an authorized alternative.
**Anti-pattern:** “Retry failures a few times, then escalate.” It defines neither a retry limit nor a required change, so identical failures can loop indefinitely.
